# 4. ✍️ Git Best Practices

Понимание команд — это база. Умение использовать их культурно и эффективно — это признак хорошего разработчика.

---


## 1. 🏗️ Атомарные коммиты
Один коммит должен решать **одну** задачу. 
- Плохо: Один коммит на 50 файлов, где вы поправили баг, обновили либу и перекрасили кнопку.
- Хорошо: 3 маленьких коммита.
> [!TIP]
> Атомарные коммиты легче ревьюить, легче откатывать (revert) и легче переносить (cherry-pick).

---


## 2. 📝 Conventional Commits
Пишите сообщения так, чтобы по ним можно было автоматически собрать Changelog.

**Шаблон**: `type(scope): description`

- `feat:` — Новая фича.
- `fix:` — Багфикс.
- `docs:` — Обновление документации.
- `refactor:` — Улучшение кода без смены логики.
- `style:` — Правки форматирования, отступов.
- `chore:` — Обновление зависимостей, конфигов.

---


## 3. 🗄️ Гигиена репозитория (.gitignore)
Никогда не коммитьте:
- Зависимости (`node_modules`, `vendor`).
- Секреты (`.env`, ключи API).
- Локальные конфиги IDE.
- Бинарные файлы сборки (`.exe`, `.log`).

---


## 4. 🚀 Полезные советы
- **Пушьте часто**: Не держите код локально неделю. Коллеги должны видеть ваш прогресс, чтобы избежать конфликтов в будущем.
- **Ревью самого себя**: Перед тем как сделать коммит или PR, сделайте `git diff`. Иногда там можно найти забытый `fmt.Println` или закомментированный код.
- **Squash коммитов**: Если вы сделали 10 коммитов вида "fix typo", "fix again", перед мерж в основную ветку схлопните их в один красивый коммит (`rebase -i`).
