# 3. 🔀 Ветки, Слияния и Конфликты

Ветки — это "киллер-фича" Git. Они невероятно легкие и позволяют изолировать разработку разных задач.

---


## 1. ⚔️ Merge vs Rebase

Это вечный спор разработчиков. Оба инструмента делают одно и то же (объединяют изменения), но разными путями.


### 1.1. Merge (Слияние)
Создает специальный **Merge Commit**, у которого два родителя.
- **Плюсы**: Сохраняет историю в первозданном виде (понятно, когда ветка началась и закончилась). Неинвазивно.
- **Минусы**: В больших проектах история превращается в "гордиев узел" из переплетенных веток.


### 1.2. Rebase (Перебазирование)
Берет ваши коммиты и "переклеивает" их к новому основанию (последнему коммиту в целевой ветке).
- **Плюсы**: Идеально линейная, чистая история. Читать `git log` — одно удовольствие.
- **Минусы**: Переписывает историю (меняет хеши коммитов). Рискованно при работе в команде.

> [!CAUTION]
> **Золотое правило**: Никогда не делайте rebase веток, которые вы уже отправили (push) в общий репозиторий. Это сломает историю всем вашим коллегам.

---


## 2. 🛡️ Conflict Resolution (Решение конфликтов)

Конфликт случается, когда два человека изменили **одну и ту же строку** в одном файле.


### Как это выглядит?
Git вставляет в файл специальные маркеры:
```text
<<<<<<< HEAD
Мой код (то, что у меня сейчас)
=======
Код из вливаемой ветки (то, что пришло)
>>>>>>> feature-branch
```


### Алгоритм решения:
1. Открыть конфликтный файл.
2. Выбрать нужный кусок (или объединить их).
3. Удалить все маркеры (`<<<<`, `====`, `>>>>`).
4. `git add <file>`
5. `git commit` (для merge) или `git rebase --continue`.

---


## 3. 🗺️ Git Flow (Популярная стратегия)

Чтобы команда не путалась, используют стандарты именования веток:
- `main` / `master` — Код, который прямо сейчас на сервере (production).
- `develop` — Основная рабочая ветка.
- `feature/*` — Ветки для новых задач.
- `hotfix/*` — Срочные правки багов в проде.
