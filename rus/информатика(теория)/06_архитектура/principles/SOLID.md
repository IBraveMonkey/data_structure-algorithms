# SOLID: Пять столпов качественного кода 🏛️

SOLID — это аббревиатура пяти принципов объектно-ориентированного программирования и дизайна, которые помогают сделать код более понятным, гибким и поддерживаемым.

---


## 1. 🎯 S: Single Responsibility Principle (Принцип единственной ответственности)
> У класса (или функции) должна быть только одна причина для изменения.

**Простыми словами:** Один компонент должен отвечать только за одну задачу. Если класс умеет и считать зарплату, и сохранять её в БД, и слать Email — это "Божественный объект", который упадет от любого изменения.


#### ❌ Плохо:
Класс `User` делает слишком много.
```go
type User struct {
    Name string
}

func (u *User) SaveToDB() { /* ... */ }
func (u *User) SendEmail() { /* ... */ } // User не должен уметь слать почту!
```


#### ✅ Хорошо:
Разделяем логику.
```go
type User struct {
    Name string
}

type UserRepository struct {} // Отвечает за БД
func (r *UserRepository) Save(u *User) {}

type EmailService struct {} // Отвечает за почту
func (s *EmailService) Send(u *User) {}
```

---


## 2. 🔓 O: Open/Closed Principle (Принцип открытости/закрытости)
> Программные сущности должны быть открыты для расширения, но закрыты для модификации.

**Простыми словами:** Вы должны иметь возможность добавить новую фичу, не меняя старый (уже протестированный) код.


#### ❌ Плохо:
Чтобы добавить новый вид уведомления, нужно править `SendNotification`.
```go
func SendNotification(msg string, tool string) {
    if tool == "email" { /* ... */ }
    if tool == "sms" { /* ... */ } // Придется дописывать if здесь каждый раз
}
```


#### ✅ Хорошо:
Используем интерфейс.
```go
type Notifier interface {
    Notify(msg string)
}

// Теперь мы просто создаем новую структуру, не трогая основной код
type TelegramNotifier struct {}
func (t TelegramNotifier) Notify(msg string) { /* ... */ }
```

---


## 3. 🔄 L: Liskov Substitution Principle (Принцип подстановки Барбары Лисков)
> Объекты в программе должны быть заменяемы на экземпляры их подтипов без изменения правильности работы программы.

**Простыми словами:** Если у вас есть функция, принимающая "Птицу", она должна работать и со "Страусом", даже если страус не летает. Если архитектура ломается при замене одного наследника на другого — принцип нарушен.


#### ❌ Типичный пример-ошибка:
Прямоугольник и Квадрат. Квадрат — это прямоугольник, но если функция `SetWidth` у Квадрата меняет и высоту, то она сломает логику, ожидающую поведения обычного Прямоугольника.

---


## 4. ✂️ I: Interface Segregation Principle (Принцип разделения интерфейса)
> Клиенты не должны зависеть от методов, которые они не используют.

**Простыми словами:** Лучше много маленьких специализированных интерфейсов, чем один огромный "универсальный".


#### ❌ Плохо:
```go
type Worker interface {
    Work()
    Eat() // Роботу не нужно есть! ❌
}
```


#### ✅ Хорошо:
```go
type Workable interface { Work() }
type Eatable interface { Eat() }

type Robot struct {} // Реализует только Workable
```

---


## 5. 💉 D: Dependency Inversion Principle (Принцип инверсии зависимостей)
> Модули верхнего уровня не должны зависеть от модулей нижнего уровня. Оба должны зависеть от абстракций.

**Простыми словами:** Не привязывайтесь к конкретным реализациям (Postgres, Redis). Привязывайтесь к интерфейсам. (Это мы подробно разбирали в теме DI/IoC).

---


### 🎯 Итог

**SOLID** — это не суровый закон, а ориентир. Иногда ради простоты (KISS) можно слегка отступить от SOLID в маленьких проектах.
