# ✍️ Как писать хорошие тесты (Writing Tests)

Написание тестов — это искусство. Хорошие тесты помогают разработке, плохие — только мешают, становясь обузой при каждом изменении кода.


# 1. 🏷️ Соглашения о именовании

В Go приняты строгие правила:
1.  **Имя файла**: Всегда `имя_файла_test.go`.
2.  **Имя функции**: Всегда `TestXxx`, где `Xxx` начинается с большой буквы.
    *   Рекомендуется: `TestMethodName_Scenario` (например, `TestUser_Save_ValidData`).
3.  **Пакет**:
    *   `package user`: Если тест должен иметь доступ к неэкспортируемым (приватным) полям.
    *   `package user_test`: Если вы тестируете только публичный API (black-box testing). Это предпочтительный вариант.


# 2. 🧱 Паттерн AAA (Arrange, Act, Assert)

Это стандарт структуры любого теста, который делает его читаемым.

```go
func TestCalculateBonus(t *testing.T) {
    // 1. Arrange (Подготовка)
    // Подготавливаем входные данные и окружение
    salary := 1000.0
    performance := 1.5
    expectedBonus := 1500.0

    // 2. Act (Действие)
    // Вызываем тестируемую функцию
    result := CalculateBonus(salary, performance)

    // 3. Assert (Проверка)
    // Проверяем результат
    if result != expectedBonus {
        t.Errorf("got %f, want %f", result, expectedBonus)
    }
}
```


# 3. 📂 Организация тестов


### Setup и Teardown
Иногда нужно выполнить код до или после всех тестов в пакете (например, поднять базу). Для этого используется функция `TestMain`.

```go
func TestMain(m *testing.M) {
    setup() // подготовка
    code := m.Run() // запуск всех тестов
    teardown() // очистка
    os.Exit(code)
}
```

Для отдельных тестов используйте `t.Cleanup`:
```go
func TestWithFile(t *testing.T) {
    f := createTempFile()
    t.Cleanup(func() {
        os.Remove(f.Name()) // выполнится в конце теста
    })
}
```


# 4. ✨ Рекомендации (Best Practices)

1.  **Тестируйте поведение, а не реализацию**: Не проверяйте, как функция работает внутри, проверяйте, ЧТО она возвращает на выходе.
2.  **Минимум логики в тестах**: В тестах не должно быть циклов `for` (кроме табличных тестов) и сложных условий `if/else`. Тест должен быть "плоским" и понятным с первого взгляда.
3.  **Изоляция**: Один тест не должен зависеть от результата другого.
4.  **Детерминизм**: Тест должен всегда возвращать один и тот же результат при одних и тех же входных данных. Избегайте использования текущего времени `time.Now()` напрямую (используйте инъекцию времени или моки).

> [!IMPORTANT]
> Самый лучший тест — это тот, который вы написали ДО того, как начали писать сам код (TDD — Test Driven Development). Это заставляет вас сначала подумать об интерфейсе и требованиях.
