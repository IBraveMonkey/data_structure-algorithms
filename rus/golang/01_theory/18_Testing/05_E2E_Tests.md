# 🏁 E2E-тесты (End-to-End Tests)

End-to-End тесты — это вершина нашей пирамиды. Они проверяют систему целиком, от интерфейса (или API) до самого глубокого уровня базы данных, имитируя поведение реального пользователя.


# 1. 🎯 Цель E2E-тестирования

E2E-тесты отвечают на главный вопрос: **"Работает ли бизнес-сценарий целиком?"**.

Пример цепочки:
1.  Пользователь регистрируется.
2.  Получает письмо с подтверждением.
3.  Логинится в систему.
4.  Создает заказ.

Если на любом из этапов (база, почтовый сервис, фронтенд, бэкенд) возникнет проблема, E2E-тест это обнаружит.


# 2. 📅 Когда использовать E2E-тесты?

Поскольку они медленные и дорогие, ими не стоит покрывать всё подряд.

**Хорошие кандидаты для E2E:**
*   **Critical Path**: Самые важные сценарии (оплата, регистрация).
*   **Сложные интеграции**: Где задействовано более 3-4 микросервисов.
*   **Smoke tests**: Быстрая проверка после деплоя, что основные функции "живы".


# 3. 🛠️ Инструменты в Go

Хотя Go часто используется для серверной логики, есть инструменты для полного тестирования:

1.  **Playwright / Selenium / Cypress**: Обычно используются для тестирования Web-интерфейса. Для Go есть биндинги, например [playwright-go](https://github.com/playwright-community/playwright-go).
2.  **Godog (Cucumber)**: Позволяет писать тесты на языке Gherkin (Given/When/Then), что удобно для согласования бизнес-логики.


### Пример Smoke-теста на Go

Для API-сервиса E2E тест может выглядеть как запуск всего приложения и выполнение реальных HTTP-запросов к нему.

```go
func TestEndToEnd_ComplexScenario(t *testing.T) {
    // 1. Поднимаем инфраструктуру (Docker Compose или TestContainers)
    // 2. Запускаем само приложение
    app := StartApp()
    defer app.Stop()

    client := &http.Client{}

    // Шаг 1: Регистрация
    resp, _ := client.Post("http://localhost:8080/register", "application/json", body)
    assert.Equal(t, http.StatusCreated, resp.StatusCode)

    // Шаг 2: Проверка состояния в базе (через API)
    resp, _ = client.Get("http://localhost:8080/profile")
    // ...
}
```


# 4. ⚠️ Проблемы E2E-тестов

*   **Хрупкость (Brittleness)**: Изменение текста на кнопке или задержка сети в 1 секунду может "уронить" тест.
*   **Сложность настройки**: Нужно подготовить состояние всех зависимостей (базы, кэш, имитация внешних API).
*   **Время выполнения**: Могут идти минуты или даже часы.

> [!TIP]
> Старайтесь держать количество E2E тестов минимальным. Если вы можете проверить логику на уровне Unit или Integration тестов — делайте это там. E2E — это "последняя линия обороны".
