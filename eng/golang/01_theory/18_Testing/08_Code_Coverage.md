# 🟢 Code Coverage

Code Coverage is a metric that shows what percentage of your source code was executed during a test run.


# 1. ❓ Why Measure Coverage?

1.  **Finding "Blind Spots"**: You see which parts of the code (especially complex `if/else` conditions) have never been verified.
2.  **Removing Dead Code**: If code cannot be covered by tests, it might never be used and can be removed.
3.  **Quality Assessment**: High coverage does not guarantee absence of bugs, but low coverage certainly guarantees their presence.


# 2. 🛠️ `go test -cover` Command

In Go, coverage tools are built directly into the toolchain.

*   `go test -cover .`: Shows the overall coverage percentage for the package.
*   `go test -coverprofile=coverage.out ./...`: Runs tests and saves detailed information to a file.


# 3. 📊 Coverage Visualization

Numbers in the terminal are not always convenient. Go allows you to generate an HTML report where you can see every line of code.

1.  Generate a profile: `go test -coverprofile=cp.out`
2.  Open it in a browser: `go tool cover -html=cp.out`

On the opened page:
*   **Green**: Code executed by tests.
*   **Red**: Code skipped.
*   **Grey**: Code that cannot be tested (type declarations, etc.).


# 4. ✨ Recommendations and Best Practices


### When Does 100% Coverage Not Make Sense?
Striving for 100% often leads to writing "useless" tests that just run the code but don't verify anything.

**Examples that are difficult or unnecessary to cover at 100%:**
*   Simple getters and setters.
*   Handling of fatal system errors that are almost impossible to reproduce.
*   Code generated by other tools.


### The "Golden Mean"
For most projects, **70-80%** is considered a good indicator. Main focus should be on complex business logic, not auxiliary code.

> [!IMPORTANT]
> Qualitative tests are more important than quantitative coverage. Coverage shows that a line *was executed*, but it doesn't guarantee that its *correctness was verified*.
